## 2. Read confinement and Codex_Home exclusion (verified for dirs; one caveat)
- Legacy modes do NOT confine reads: under both `read-only` (ro turn 2, 22:27:29) and `workspace-write` (ww turn 4, 22:27:57), `cat outside/canary.txt` printed `CANARY-OUTSIDE-51a7` (exit 0). Whole-filesystem read is the default there.
- Confinement is possible with a named permission profile in `config` (`default_permissions` + `permissions.<id>.filesystem`; must not be combined with `sandbox`). Run `prof` (pixie-spike-sbx-prof, final run 22:44:40-22:45:23), profile `pixie_confined` = `{":minimal": read, <codex bin dir>: read, allowed: read, ws: write, fakehome: deny}`:

  - read `outside/canary.txt` (22:44:47): `No such file or directory`, exit 1. The unlisted directory is not visible in the sandbox mount view (confinement by omission).
  - read `ws/link-outside.txt`, a symlink in ws to the outside canary (22:44:59): `No such file or directory`, exit 1 (symlink does not bypass).
  - read via script `ws/readoutside.sh` (22:45:07): `cat: ... No such file or directory`, exit 1.
  - write in ws (22:45:13): exit 0, file exists. Write to `outside/oob2.txt` (22:45:17): "Directory nonexistent", exit 2, file absent.
  - The `:minimal` base alone made every command fail with `bwrap: execvp <codex binary>: No such file or directory` (first `prof` run, 22:28:01-22:28:31; its raw file was overwritten by the later run, so this is from my transcript, not a saved file). Whether other host paths (shared libs, `/etc`, interpreters the task needs) must be listed for real tasks: not verified; only `sh`/`cat`/`echo` were exercised.
- Excluding the Codex_Home from reads (stand-in "fakehome" dir, explicit `deny`): run `profdeny2` (pixie-spike-sbx-profdeny2, 22:47:13-22:47:24), profile `pixie_denyhome` = `extends ":workspace"` + `{fakehome: deny}`, fresh thread, neutral script `ws/job1.sh` (the model did not know it read fakehome): `cat fakehome/canary.txt` -> `Permission denied`, exit 1 (22:47:14). ## 4. Sandbox cannot be applied (verified by simulation; real host not affected)
- Reproduction without changing the system: transient unit property `RestrictNamespaces=user` (seccomp denies creating user namespaces for that unit only). Run `nosb` (pixie-spike-sbx-nosb, 22:48:38-22:48:51), `workspace-write` as in section 1, `approvalPolicy=never`.
- Observed: both attempted writes (in cwd 22:48:39-22:48:46; outside 22:48:46-22:48:51) failed with `bwrap: No permissions to create a new namespace, likely because the kernel does not allow non-privileged user namespaces ...`, command item status `failed`, exit 1, files absent. The thread started without error and the turn status was `completed`. So the backend fails closed (no silent fallback to running unsandboxed) for commands, but there is no startup error or typed signal: the failure shows only as a command-item failure and the model's text. The Runtime's start-up probe (Doctor `--probe` or a sandbox canary at worker start) must detect this; a run cannot be assumed safe from "thread started" alone (supports Requirement 8.13 fail-closed handling).
- Distinct real-host causes (AppArmor `apparmor_restrict_unprivileged_userns`, sysctl disabling userns, missing bwrap): only the seccomp-simulated case was run; the others are "not verified" (would need system changes; not allowed).
